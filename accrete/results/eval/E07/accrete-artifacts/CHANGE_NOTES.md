# E07 Preventive maintenance schedules

Interpretation: new `schedules` entity (asset ref, required and immutable; title; priority p1-p4; interval_days a JSON integer from 1 to 365; next_due a real date; active, default true). Everyone can read schedules. Create, PATCH and DELETE are for managers and for supervisors of the asset's site. For a create, an existing asset at another site gives 403 before any 400; an unknown asset gives 400. A retired asset gives 400. p4 on a high-criticality asset gives 400, on create and on any PATCH that sends p4, as for work orders. Sending `asset` in a PATCH gives 400.
Work orders get a read-only (system) `schedule` reference, which is null for all 82 existing orders. Because it is a reference, deleting a schedule that has generated an order gives 409, and deleting an asset that has any schedule gives 409.
`generate` action: the allow rule (403) is manager or own-site supervisor. The guard (409) requires the schedule to be active, its asset not retired, no unfinished order generated by this schedule, and today >= next_due - 7 days. In one atomic step it creates the work order (description "Preventive maintenance", status open, requested_by the caller), emits `preventive_generated` {schedule, work_order, next_due (the new value)}, and advances next_due by interval_days exactly once.
An asset trigger: a PATCH that sends `retired: true` sets active=false on all of that asset's schedules in the same operation. The existing open-orders 409 still wins. Un-retiring the asset does not reactivate them.
Data: schedules 1-5 created as specified. No other record changed.
